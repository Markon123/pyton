# ОренКод · платформа ФСП Оренбургской области

Рабочий демонстрационный MVP на Python/Django: календарь соревнований, заявки, результаты и протоколы, реестр, разряды и судейские категории, рейтинг и сборная. Интерфейс на русском языке, адаптирован для компьютера и телефона. Все демонстрационные участники, организации, приказы и результаты вымышлены.

Проект реализует основные сквозные процессы кейса, но не является готовой к промышленному внедрению системой и не закрывает все дополнительные модули исходного ТЗ. Конкретные ограничения приведены ниже.

## Быстрый запуск

Для проверки на своём компьютере распакуйте архив и запустите **`start-demo.bat` в Windows** или **`bash start-demo.sh` в macOS/Linux**. Нужны Python 3.12 или новее и интернет для первой установки пакетов. Лаунчер подготовит базу и сам откроет браузер; окно запуска оставьте открытым. Подробности и разбор ошибок: [docs/local-launch.md](docs/local-launch.md).

Требуется Python 3.12 с модулем `venv`. В существующем checkout репозитория:

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo
python manage.py runserver 0.0.0.0:8000
```

Откройте приложение на порту `8000`; страница входа — `/login/`. Состояние приложения и доступ к таблицам БД проверяет `GET /health/` с ответом `{"status": "ok"}`. Для работы не требуются внешние сервисы или ключи. Даты и сроки рассчитываются в часовом поясе `Asia/Yekaterinburg`.

Для повторяемой настройки есть `bash scripts/setup.sh`: установка закреплённых зависимостей, миграции и системная проверка. Демо-наполнение включается явно: `FSP_SEED_DEMO=1 bash scripts/setup.sh`. Затем `bash scripts/start.sh` проверяет приложение, формирует напоминания и запускает сервер разработки. По умолчанию используется `.venv`; в подготовленной облачной среде задайте `FSP_VENV_DIR=/workspace/.venvs/pyton` для обеих команд. Адрес сервера можно задать через `FSP_BIND=0.0.0.0:8000`. Используйте существующий checkout: отдельное Git worktree для облачной задачи не требуется.

`seed_demo` можно запускать повторно: команда добавляет недостающие демонстрационные записи, не сбрасывает существующие пароли и изменения. Она создаёт 6 дисциплин, 4 организации, 27 профилей, 8 соревнований, примеры результатов, заявок, тренерских связей и разрядов. Даты начального наполнения привязаны к дате первого запуска; повторное наполнение не переносит сроки уже созданных соревнований.

## Демонстрационные аккаунты

У всех четырёх аккаунтов пароль **`FspDemo2026!`**.

| Логин | Роль и назначение |
| --- | --- |
| `federation` | Все четыре роли; начальная роль — федерация. Создание соревнований, модерация, реестр, отчёты и сборная |
| `athlete` | Спортсмен: профиль, заявки, опубликованные результаты, согласия, разряд |
| `coach` | Тренер: подтверждённые связи со спортсменами, заявки и разряды подопечных |
| `judge` | Судья: категория, заявки на её присвоение, назначения на соревнования |

У аккаунта `federation` переключайте активную роль в меню кабинета без повторного входа. Приложение проверяет именно активную роль: после переключения в спортсмена административные действия недоступны. Самостоятельная регистрация на `/register/` разрешает роли спортсмена, тренера и судьи; роль федерации через неё получить нельзя.

Техническая админка Django `/admin/` отделена от кабинета федерации и требует служебных разрешений Django. Демо-аккаунты их не получают. Для технического администратора создайте отдельную учётную запись:

```bash
python manage.py createsuperuser
```

Она не получает автоматически профиль или роли приложения. Не используйте техническую админку для обычных бизнес-процессов: её операции не проходят через журнал бизнес-действий и проверки активной роли.

## Что и где проверить

| Сценарий | Действия в интерфейсе |
| --- | --- |
| Соревнование → протокол | Федерацией откройте `/competitions/new/`, задайте дисциплину, возраст, даты и положение PDF/DOCX, откройте приём заявок. Спортсменом подайте заявку из карточки соревнования. Федерацией одобрите её, закройте регистрацию, внесите место и баллы для каждого допущенного участника, опубликуйте протокол. У спортсмена результат появится в `/profile/` |
| Разряд → приказ | В `/qualifications/` подайте заявку с результатом из опубликованного протокола. При действующей связи с тренером по дисциплине заявку подаёт тренер. Федерация рассматривает её и указывает дату присвоения, срок действия и номер приказа. Для судей на той же странице доступна заявка на категорию |
| Тренер → спортсмен | В `/coaching/` тренер запрашивает связь по дисциплине; спортсмен подтверждает её в своём кабинете. Только после подтверждения тренер может подавать заявки за этого спортсмена по этой дисциплине |
| Рейтинг → сборная | В `/rating/` выберите сезон, дисциплину и возраст. Раскройте расчёт баллов, отметьте спортсменов, сформируйте сборную и скачайте состав с проектом приказа. Баллы за места 1–3 настраивает федерация; минимум два призовых выступления на разных соревнованиях дают коэффициент ×1,2 |
| Реестр и история | `/registry/`: поиск, фильтры, спортсмены, тренеры, судьи и организации. Личная карточка и её выгрузка доступны самому владельцу, его действующему тренеру и федерации в предусмотренных ролях |
| Численность | Федерацией откройте `/reports/`, выберите период минимум за два года, при необходимости дисциплину и организацию, скачайте XLSX/DOCX/PDF |
| Уведомления и аудит | `/notifications/` — уведомления текущего пользователя; `/audit/` — журнал действий для федерации с пользователем, временем, активной ролью и объектом |
| Дополнительный модуль Д11 | `/guide/` — навигатор новичка: дисциплины, первые шаги и переход к календарю. Доступен после входа |

Готовые прошедшие соревнования содержат опубликованные протоколы. Подробная последовательность приёмки: [docs/acceptance.md](docs/acceptance.md). Скачивание протоколов, составов сборной, истории выступлений, численности и подтверждений согласий доступно в XLSX, DOCX и PDF. Это демонстрационные формы; [описание экспорта](docs/document-templates.md) поясняет их ограничения.

## Проверки

В активированном виртуальном окружении:

```bash
python manage.py check
python manage.py test
```

Тесты используют отдельную временную базу. Они проверяют сквозные процессы, ограничения активной роли и доступа к чужим данным, согласия, тренерские связи, допуск участников, целостность протокола, рейтинг и содержимое экспортируемых файлов. Документация модели и интерфейсов: [docs/architecture.md](docs/architecture.md).

Зависимости, включая транзитивные, закреплены в `requirements.txt`. Основные версии: Django 5.2.18, openpyxl 3.1.5, python-docx 1.2.0, ReportLab 4.4.10; Gunicorn 23.0.0 включён для развёртывания. Встроенные шрифты позволяют формировать PDF с кириллицей без обращения к CDN.

## Почта и регулярные напоминания

По умолчанию используется файловый backend Django: письма сохраняются в `.local/mail/`. Это транспорт для разработки; **реальной внешней доставки в этой конфигурации нет**. Внутренние уведомления сохраняются независимо от успешности отправки письма.

Для настоящей доставки передайте настройки SMTP через окружение процесса, например:

```bash
export EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
export EMAIL_HOST=smtp.example.org
export EMAIL_PORT=587
export EMAIL_USE_TLS=1
```

Также задайте `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` и `DEFAULT_FROM_EMAIL` через безопасные настройки среды. Не сохраняйте реальные пароли в репозитории. После настройки проверьте доставку на разрешённый адрес; наличие настроек само по себе её не подтверждает.

Напоминания об истечении разрядов/категорий в ближайшие 30 дней и приближающемся закрытии регистрации формируются командой:

```bash
python manage.py send_reminders
```

Повторный запуск не создаёт одинаковые напоминания. Для регулярной работы настройте ежедневный планировщик; он не устанавливается автоматически. Пример cron при расположении проекта `/workspace/pyton` и окружения `.venv`:

```cron
0 9 * * * cd /workspace/pyton && .venv/bin/python manage.py send_reminders >> .local/reminders.log 2>&1
```

Это `09:00` в часовом поясе cron. Настройте нужный часовой пояс планировщика и передайте ему те же переменные SMTP/БД, что и приложению. В облачных задачах фоновые процессы и cron не следует считать сохранёнными после восстановления снимка.

## Локальные данные и настройки

SQLite находится в `.local/db.sqlite3`, положения — в `.local/uploads/`, письма — в `.local/mail/`. Каталог `.local/` и виртуальные окружения исключены из Git. Для другого файла БД задайте `DATABASE_PATH`. Файлы положений выдаются авторизованным пользователям через приложение, без публичного каталога загрузок.

Шаблон переменных — `.env.example`. Произвольный файл `.env` **не загружается автоматически**: значения нужно экспортировать в окружение процесса или передать средствами хостинга.

Для резервной копии SQLite используйте его backup API, чтобы получить согласованный снимок работающей БД:

```bash
python - <<'PY'
import os
import sqlite3
from datetime import datetime
from pathlib import Path

source_path = Path(os.environ.get('DATABASE_PATH', '.local/db.sqlite3')).resolve()
backup_dir = Path('.local/backups')
backup_dir.mkdir(parents=True, exist_ok=True)
target = backup_dir / f'db-{datetime.now():%Y%m%d-%H%M%S}.sqlite3'
with sqlite3.connect(source_path.as_uri() + '?mode=ro', uri=True) as source:
    with sqlite3.connect(target) as destination:
        source.backup(destination)
print(target)
PY
```

Сохраняйте резервные копии вне машины вместе с файлами `.local/uploads/`; периодически проверяйте восстановление. Письма разработки не заменяют резервное копирование базы и файлов.

## Границы MVP и внедрение

- Официальные формы протоколов и приказов не приложены к кейсу. Экспорт содержит демонстрационные таблицы и пометки о вымышленных данных; для внедрения нужны утверждённые шаблоны, подписанты и согласование полей.
- Внешний канал предусмотрен через SMTP, но сервер и реальные реквизиты не настроены. Файловая почта не закрывает требование внешней доставки.
- Рейтинг и сборная формируются отдельно по дисциплине. Разряды назначаются сотрудником по указанному результату; автоматической проверки нормативов ЕВСК нет.
- Динамика численности строится по интервалам `start_year`–`end_year`. При фильтрации используется текущая организация и набор дисциплин, исторические переходы между ними не моделируются.
- Используются сессионная авторизация Django и CSRF, а не JWT. JSON API ограничен чтением списка соревнований; остальные процессы работают через HTML-формы.
- OIDC/ФСП ID, интеграции с Госуслугами, апелляции, премии и другие дополнительные модули не реализованы. Само наличие согласий в демоверсии не является подтверждением юридического соответствия требованиям к ПДн.

Перед промышленным развёртыванием замените демонстрационные аккаунты/данные, настройте отдельный сервер приложений и HTTPS, `DJANGO_DEBUG=0`, уникальный `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, раздачу статики после `collectstatic`, резервное копирование и мониторинг. `runserver` предназначен для разработки. Для PostgreSQL потребуется добавить драйвер и конфигурацию БД, применить миграции и проверить перенос данных; текущее приложение настроено на SQLite, переменная `DATABASE_URL` не поддерживается. Выполните `python manage.py check --deploy` с реальными настройками развёртывания.
