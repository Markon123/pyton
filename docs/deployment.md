# Развёртывание и резервное копирование

## Локальная демонстрация Docker

Нужны Docker Engine с Compose v2 и доступ к реестрам образов/PyPI. Все фикстуры вымышлены. Из корня проекта:

```bash
docker compose --env-file deployment/demo.env --profile mail up --build -d
docker compose ps
docker compose logs --tail=80 app scheduler
```

Сервисы: PostgreSQL 16, приложение Gunicorn, планировщик, опциональный SMTP-приёмник Mailpit. Приложение доступно на локальном порту `8000`, почтовый интерфейс — `8025`; наружу эти порты привязаны только к loopback. Это не публикация сайта и не пользовательский облачный preview. При первом старте применяются миграции, собирается статика и создаются демонстрационные данные. Данные PostgreSQL и `.local` приложения лежат в именованных томах. Обычный `docker compose down` их сохраняет; `down -v` удалит данные, поэтому не используйте этот флаг для обычной остановки.

Приложение работает непривилегированным Linux-пользователем `app`. `.local` содержит загруженные подтверждения, OIDC-ключ и собранную статику; этот каталог не включается в образ из рабочей машины и не попадает в Git. Вебхуки не отправляются на произвольные URL: отдельный список разрешённых HTTPS-хостов задаётся параметром `INTEGRATION_WEBHOOK_ALLOWED_HOSTS`.

При сборке за корпоративным HTTPS-прокси передайте стандартные proxy build-args и доверенный CA bundle через опциональный BuildKit secret `build_ca`. Dockerfile использует его для APT и pip только в момент сборки; сертификаты и реквизиты прокси не копируются в образ. Пример: `docker build --build-arg HTTPS_PROXY --build-arg HTTP_PROXY --secret id=build_ca,src=/path/to/trusted-ca.pem -t orenkod:local .`. Файл должен содержать именно доверенные публичные CA-сертификаты. Не отключайте проверку TLS или подписей пакетов при ошибке доверия.

## Рабочий сервер

Подготовьте DNS и доверенный HTTPS reverse proxy. Репозиторий не создаёт домен, сертификат и хостинг автоматически. Развёртывайте на чистой БД без демоданных. Создайте конфигурационный файл вне Git, доступный только администратору, с уникальными `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, `PUBLIC_BASE_URL` и параметрами реального SMTP. Для пароля БД в текущем Compose выбирайте длинную случайную строку из URL-безопасных символов (например, hex); если собираете собственный `DATABASE_URL`, специальные символы логина/пароля нужно URL-кодировать. `.env.example` содержит только имена и несекретные примеры.

```bash
docker compose --env-file /secure/orenkod.env -f compose.yaml -f deployment/compose.production.yaml up --build -d
docker compose exec app python manage.py check --deploy
docker compose exec app python manage.py createsuperuser
```

Production override требует секрет и домены, включает `DJANGO_DEBUG=0` и запрещает автоматическое демо-наполнение. Приложение принимает подключения от локального reverse proxy; PostgreSQL и файлы загрузок не выдаются публично. `TRUST_PROXY_HEADERS=1` включайте только за доверенным proxy, который удаляет входящие заголовки клиента и сам устанавливает `X-Forwarded-Proto`. Передайте это значение и приложению, и планировщику в своей конфигурации Compose. Политики HTTPS/HSTS и secure cookies настраиваются в Django. Проверяйте `check --deploy` с фактической конфигурацией: успешная сборка образа не подтверждает корректный DNS, TLS и доставку почты.

Добавьте действительный домен и `127.0.0.1` к `DJANGO_ALLOWED_HOSTS`, чтобы внутренний healthcheck мог обращаться к приложению. Healthcheck должен быть исключён из принудительного перенаправления HTTP→HTTPS, иначе проверка из контейнера будет перенаправлена на отсутствующий внутренний TLS. Проверяйте HTTP `GET /health/` и реальный вход через HTTPS после выкладки. `.local/oidc` должен быть постоянным между перезапусками: замена ключа делает ранее подписанные OIDC-токены непроверяемыми.

Для самостоятельного запуска без Docker доступны `DATABASE_URL` с PostgreSQL и `DATABASE_PATH` с SQLite. `DATABASE_URL` имеет вид `postgresql://user:password@host:5432/database?sslmode=verify-full`; для удалённой БД используйте подходящую проверку TLS и доверенный корневой сертификат. Статику собирает `python manage.py collectstatic --noinput`, раздаёт WhiteNoise. Используйте Gunicorn, а не сервер разработки Django.

## Резервные копии

```bash
python manage.py backup_database
# либо в контейнере:
docker compose exec app python manage.py backup_database
```

Для SQLite используется backup API, позволяющий получить согласованную копию работающей базы. Для PostgreSQL — `pg_dump` в custom-формате; клиент версии 16 установлен в Docker-образе из официального образа PostgreSQL 16, чтобы дамп можно было восстановить на том же сервере 16. Пароль передаётся процессу через `PGPASSWORD`, а не аргументы командной строки; команда не печатает DSN/реквизиты. Выходной файл создаётся с режимом `0600`, существующий файл не перезаписывается, старые резервные копии автоматически не удаляются. `--output` позволяет выбрать новый путь.

Храните копию **вне машины** вместе с `.local/uploads`, другими защищёнными файлами модулей и `.local/oidc`. Установите расписание и срок хранения по своим требованиям. Резервная копия на том же диске не защищает от его потери.

Восстановление выполняйте в **новую пустую БД**, затем проверяйте вход, количество записей, файлы, протокол и сертификаты. Для SQLite остановите приложение и замените файл только после проверки копии `PRAGMA integrity_check`; сохраните старую БД отдельно. Для PostgreSQL используйте `pg_restore --no-owner --no-privileges --dbname <new_database> <backup.dump>` с реквизитами в безопасном окружении; не направляйте эту команду в рабочую БД. После восстановления файлов и базы выполните миграции и функциональную проверку.

## Автоматическая проверка

`.github/workflows/ci.yml` содержит отдельные проверки Python 3.12 на Windows/Ubuntu с SQLite и Ubuntu/PostgreSQL 16. Проверяются миграции, фикстуры, тесты и переносимый лаунчер без открытия браузера. Наличие workflow в Git не означает, что удалённый запуск GitHub Actions уже прошёл: результат проверяйте на вкладке Actions конкретного коммита. Нативная проверка Windows выполняется этим workflow, а не объявляется выполненной в Linux-среде разработки.

## Публичный HTTPS на своём сервере

Подготовлен полный стек с Caddy и автоматическим сертификатом. До запуска нужно направить DNS-имя на сервер, установить Docker Compose и обеспечить доступ к портам 80/443. Команды выполняются на этом сервере, в распакованном проекте:

```bash
python scripts/configure_deployment.py --domain platform.your-domain.ru
# В .env.production безопасно заполните реальные настройки SMTP, когда они предоставлены.
docker compose --env-file .env.production -f compose.yaml -f deployment/compose.production.yaml -f deployment/compose.public.yaml up --build -d
docker compose --env-file .env.production -f compose.yaml -f deployment/compose.production.yaml -f deployment/compose.public.yaml exec app python manage.py bootstrap_federation --username owner --email owner@your-domain.ru
```

Генератор создаёт отдельные случайные секреты с закрытыми правами, не выводит их и не перезаписывает существующий файл. `.env.production` исключён из Git и сборки Docker. `bootstrap_federation` интерактивно запрашивает пароль и согласие владельца, создаёт обычный кабинет федерации без доступа в техническую админку и отказывается менять существующие аккаунты. Публичный сайт настраивается без демонстрационных людей и фиктивных нормативов; справочники после миграций подготавливаются автоматически.

Caddy принимает HTTPS, передаёт приложению проверенный протокол соединения и сохраняет сертификаты в отдельном томе. Не используйте этот сценарий поверх существующего proxy без проверки занятых портов и конфигурации. Создание конфигурационного файла и проверка Caddy не подтверждают выдачу сертификата или публикацию: результат проверяется после настройки настоящего DNS и сервера. Для почты нужен действующий SMTP, для официальных документов и нормативов — утверждённые заказчиком значения.
