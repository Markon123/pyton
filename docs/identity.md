# Д1 · Региональный ФСП ID

ФСП ID реализован на **django-oauth-toolkit**, а не на собственном протоколе. Поддерживается OpenID Connect с потоком authorization code + обязательный **PKCE S256**, явным согласием пользователя и подписью ID token **RS256**. Implicit, password grant, динамическая регистрация клиентов и маски redirect URI отключены.

## Проверка в интерфейсе

1. Войдите в кабинет федерации и откройте раздел **ФСП ID** (`/identity/`). Создайте приложение с точным HTTPS-адресом возврата. Client ID отображается в списке; публичный клиент не использует общий секрет.
2. При локальном запуске откройте **Тестовый клиент** (`/identity/demo/`) и нажмите **Войти через ФСП ID**.
3. Провайдер покажет страницу согласия на идентификатор, имя, роли, дисциплины и действующий разряд. Нажмите **Разрешить передачу данных** либо откажите.
4. После согласия клиент обменивает код вместе с `code_verifier`, проверяет подпись по JWKS, issuer, audience, срок и nonce, затем получает `userinfo` и проверяет совпадение `sub`. На странице показаны проверенные данные без сырых токенов.
5. В разделе **Мои разрешения** (`/identity/grants/`) отзовите доступ. Access и refresh tokens этого приложения перестанут работать.

Встроенный тестовый клиент предназначен для локального DEBUG-режима. Он допускает только точный loopback-адрес и фактический порт сервера, поэтому работает и при `FSP_PORT=8001`. Порт из произвольного Host-заголовка не принимается. В промышленном режиме тестовый клиент и HTTP redirects отключены; подключается отдельное HTTPS-приложение.

## Эндпоинты

| Адрес | Назначение |
| --- | --- |
| `GET /.well-known/openid-configuration` | OIDC discovery |
| `GET /.well-known/jwks.json` | Только открытые ключи проверки подписи |
| `GET /.well-known/oauth-authorization-server` | Метаданные OAuth |
| `GET/POST /o/authorize/` | Вход и явное согласие пользователя; POST защищён CSRF |
| `POST /o/token/` | Обмен кода с PKCE или обновление токена |
| `GET/POST /o/userinfo/` | Данные пользователя по Bearer access token |
| `POST /o/revoke/` | Отзыв токена |

Запрос authorization code содержит `client_id`, точный `redirect_uri`, `response_type=code`, `scope=openid profile fsp`, случайные `state` и `nonce`, `code_challenge` и `code_challenge_method=S256`. После возврата клиент обязан проверить `state` до обмена кода. Для обмена используются `grant_type=authorization_code`, `client_id`, `code`, исходный `redirect_uri` и `code_verifier`.

Scopes ограничивают выдачу данных:

| Scope | Поля |
| --- | --- |
| `openid` | `sub` — стабильный идентификатор пользователя |
| `profile` | `name`, `given_name`, `family_name` |
| `fsp` | `roles`, `disciplines`, `current_rank` |
| `email` | `email`, только если пользователь согласовал этот scope |

Дата рождения, телефоны, представитель и иные данные профиля не выдаются. Роли в claims описывают назначенные роли аккаунта и не дают клиенту прав изменять их в платформе. Управление клиентами доступно только в **активной роли федерации**; встроенные страницы управления django-oauth-toolkit не опубликованы.

## Ключи и промышленная настройка

Закрытый RSA-ключ создаётся однократно в `.local/oidc/private.pem` с режимом `0600` на POSIX. Он исключён из Git вместе с `.local`. Команда `python manage.py setup_identity` проверяет постоянный ключ и не создаёт аккаунты или тестовые клиенты. `setup_identity --demo` явно добавляет локальный публичный клиент только в DEBUG. При необходимости передайте `--base-url` для первоначального адреса; интерфейс локальной демонстрации учитывает фактический порт.

В промышленном окружении задайте канонический HTTPS issuer через `OIDC_ISSUER`, при необходимости путь к ключу через `OIDC_PRIVATE_KEY_FILE`, сохраните ключ в постоянном защищённом хранилище и резервной копии. Не публикуйте и не пересоздавайте ключ при перезапуске контейнера: это нарушит проверку ранее выданных токенов. На Windows права доступа к папке ключа дополнительно ограничиваются средствами ОС. При ротации заранее публикуйте предыдущие открытые ключи до истечения выданных ID tokens; автоматическая ротация ключей не включена.

Поддерживаемый внешний клиент должен проверять подпись, `iss`, `aud`, `exp`, `iat`, `nonce`, а также совпадение `sub` между ID token и userinfo. Тестовый клиент выполняет эти проверки; проверка отключением TLS не используется. Access token живёт один час, ID token — десять минут, код — две минуты; обновляемые токены ротируются с защитой повторного использования.

Проверки реализации: `python manage.py test identity`. Сторонние реальные клиенты и их домены регистрируются федерацией после получения их точных HTTPS-адресов.
